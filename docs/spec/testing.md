# 测试规范 (Testing Strategy)

> **路径**：[`docs/spec/testing.md`](testing.md)  
> **用途**：规范全栈项目的测试方法、用例设计、覆盖率要求及工具链。

---

## 1. 概览

本项目严格遵循经典的测试金字塔模型：
- **单元测试 (Unit Tests)**：绝大部分的业务组件，尤其是**围棋核心规则引擎**的独立算法隔离验证。
- **集成测试 (Integration Tests)**：覆盖 Web 后端的 Router 接口到 Repository 持久层存储链路。
- **端到端测试 (E2E Tests) / 压测**：系统全流程模拟及大并发下的性能瓶颈测试。

---

## 2. 后端测试规范 (Go)

### 2.1 基础工具链
- 原生 `testing` 包，推荐配合 `t.Run` 进行子测试管理。
- 使用 `github.com/stretchr/testify/assert` 和 `require` 进行断言式测试，取代啰嗦的 `if err != nil` 报错手写。
- 对外依赖网络与缓存的服务使用 `go.uber.org/mock` 自动生成 mock 文件（配合 `go generate`）。

### 2.2 核心单元测试（规则引擎）
对于 `internal/engine` 下的围棋引擎逻辑（如打劫、气数计算、自杀禁止等），**要求达到 100% 的分支覆盖率**。
此包不依赖任何网络或存储，必须大量编写**表驱动测试 (Table-Driven Tests)**，例如定义多组残局 SGF 文本 -> 解析 -> 模拟一子 -> 断言提子数和合法性。

```bash
# 执行单元测试并查看覆盖率报表
go test -v -coverprofile=coverage.out ./internal/engine/...
go tool cover -html=coverage.out
```

### 2.3 接口集成测试
- **测试范围**：`internal/api` 等基于 HTTP 或短线 WS 通信的封装入口。
- **运行环境**：依赖真实的 MySQL 和 Redis 环境，在本地开发中直接连通 `docker-compose` 起的容器环境。
- **数据隔离**：每次执行前可以通过建立沙盒 DB、`Truncate` 洗数据，或在测试代码首尾利用 `Transaction` 回滚，确保测试状态无副作用互不干扰。

```bash
# 用 -tags 隔离集成测试，避免日常跑单测时因为没起容器报错
go test -tags=integration ./test/integration/...
```

### 2.4 测试编写进阶规范 (Best Practices)
- **命名规范**：遵循 `Test<被测函数><场景><预期结果>`，如 `TestPlaceStoneSuicideReturnsError`。
- **代码结构**：严格遵守 `Arrange-Act-Assert` (准备-执行-断言) 三段式结构。
- **杜绝 Flaky Tests (闪烁测试)**：异步测试中严禁使用 `time.Sleep` 进行固定时长盲等。必须利用 `sync.WaitGroup`、Channel 信号或 `testify` 提供的 `require.Eventually` 进行确定性等待。

## 3. 前端测试规范 (TypeScript/React)

### 3.1 基础工具链
- **端到端与大盘集成测试**：使用 **Playwright**。由于我们重度依赖 HttpOnly Cookie 和 WebSocket，Playwright 能最真实地接拉起 Chromium 环境，不仅能验证跨页面路由守卫，而且 `async/await` 原生模型更适合未来复杂的对弈和异步时序测试。
- **单元与 Store 测试**：放弃 Jest，使用与 Vite 完美集成的 **Vitest**。
- **DOM 断言 / Mock**：涉及局部组件时使用 **React Testing Library (RTL)**，使用 **msw (Mock Service Worker)** 在 Service Worker 层级强行 Mock 后端请求。

### 3.2 重点测试区域
- **大盘集成 (Playwright E2E)**：验证真实浏览器连通后的核心 Happy Path (如 注册->登录->存Cookie->跳转重定向) 及边缘流 (Token过期拦截器静默刷新行为)。
- **状态管理 (Zustand Store)**：不用挂载组件，用 Vitest 直接测试业务逻辑是否成立，如：`GameStore.dispatch(SyncBoardPayload)` 后，Store 内的倒计时、当前回合数和 19x19 的状态二维数组是否符合预期。
- **棋盘交互 (Board)**：通过 RTL 点击特定坐标，验证 onClick 输出给服务端的落子坐标（如将 DOM 界面的 XY 转化为 0-18 的 `x,y` 索引）是否正确。

```bash
# 前端单元测试（支持热重启）
npm run test
# 覆盖率检查
npm run test -- --coverage
# E2E 测试（需要后端服务运行中）
npm run test:e2e
```

### 3.3 前端测试进阶规范
- **语义化断言**：使用 `describe` 分组模块，使用 `it` 描述用例（如 `it('should render loading spinner when fetching')`）。
- **用户视角选择器 (A11y Priority)**：在使用 RTL 时，强制优先使用 `getByRole`、`getByLabelText` 等无障碍选择器定位元素。极力避免使用依赖 UI 实现细节的 CSS 类名选择器或滥用 `data-testid`。

### 3.4 跨端测试代码目录规范
**前端 (`FantasyGoWorld-FE`)：** 统一存放于根目录下的 `tests/`。
- `tests/e2e/`: 核心业务的 Playwright 集成测试和 E2E 测试脚本。
- `tests/components/`: Vitest 等涉及前端状态机和组件展示的纯单元测试。

**后端 (`FantasyGoWorld-BE`)：** 严格按照特性分层。
- **纯粹函数的单测及 API 接口测试**：强制要求代码随行（例如 `auth.go` 旁边紧挨着存放 `auth_test.go`），且需要优先脱离 DB 环境。
- **端到端的真实后端集成测试**：单独存放于后端根目录的 `test/integration/` 以便在 CI 流水线及 Docker 环境中结合依赖集中执行。

## 4. 并发压力测试 (Load Testing)

对于以**并发大厅 + 对弈实时通信**为核心的游戏业务，性能基准测试与日常压测一样重要。

- **压测工具**：`k6` (采用 Go 开发的高性能压测框架，非常适合压测 WebSocket 持续通信，相比 JMeter 更轻量敏捷)。
- **核心关注场景**：
  1. **巨量连接心跳存活**：模拟单节点 5000+ 个 User 同时在线闲置下发 PingPong 心跳，检查 Hub 单一 goroutine 的消费速度与内存占用。
  2. **高频收发验证**：模拟 1000 个房间（2000 个玩家）以极高频的速度落子，关注平均响应延迟 (Latency) 以及引擎 `PlaceStone` 判断时引起的 CPU Profiling 尖峰。

## 5. 测试用例设计规范 (Test Case Design Spec)

> 本节为完整的**测试工程方法论**落地指南，涵盖用例结构、经典设计技术、覆盖率度量和风险优先级评估。所有 P0/P1 级功能在提交 PR 前，须经过本规范约束。

---

### 5.1 测试用例标准模板 (Case Template)

每一个测试用例必须包含以下字段，**省略任何一个字段均视为不完整用例**：

| 字段 | 说明 | 示例 |
|:---|:---|:---|
| **TC-ID** | `模块-方向-序号`（P=正向，N=负向） | `TC-AUTH-N-01` |
| **标题** | `Given-When-Then` 一句话 | 给定用户名已存在，当再次注册，则返回冲突报错 |
| **优先级** | P0 / P1 / P2（见 §5.4 风险矩阵） | P0 |
| **所属层级** | 单元 / API / E2E / 压测 | E2E |
| **前置条件** | 环境与数据的初始状态 | 用户 `alice` 已注册；后端服务已启动 |
| **测试步骤** | 编号、原子化的操作序列 | 1. 访问 `/login`; 2. 切换到注册; 3. 输入 `alice`; 4. 点击提交 |
| **预期结果** | 可被 `assert` 的**具体**描述 | Toast 显示 `username already exists`；URL 停留在 `/login` |
| **清理动作** | 测试后恢复现场 | 不需要（随机用户名，无副作用） |

---

### 5.2 经典测试设计技术 (Test Design Techniques)

以下技术是行业内保障覆盖全面性的核心手段，本项目按功能类型选择适用的技术执行。

#### A. 等价类划分 (Equivalence Partitioning, EP)

**核心思想**：将输入域划分为有效等价类和无效等价类。同一个等价类内的任意值对系统的处理结果是一致的，因此只需选取一个代表值，避免冗余测试。

**应用示例：注册用户名字段（`min=4, max=50`）**

| 等价类 | 输入范围 | 代表值 | 期望结果 |
|:---|:---|:---|:---|
| 有效类 | 4 ≤ 长度 ≤ 50 | `alice` (5位) | 注册成功 |
| 无效类 1 | 长度 < 4 | `abc` (3位) | 前端拦截，Toast 长度不足 |
| 无效类 2 | 长度 > 50 | 51位字符串 | 前端或后端 `40002` 拒绝 |
| 无效类 3 | 空字符串 | `""` | 前端必填校验拦截 |
| 无效类 4 | SQL/XSS 注入 | `alice'; DROP TABLE--` | 不崩溃，注册失败或安全处理 |

**规则**：对每个等价类至少编写一个用例；有效类与无效类都不可省略。

---

#### B. 边界值分析 (Boundary Value Analysis, BVA)

**核心思想**：边界处最容易出现 off-by-one 错误（`< min` vs `<= min`）。除等价类代表值外，必须额外测试边界上下紧邻值。

**应用示例：用户名 `min=4, max=50`**

| 边界点 | 测试值 | 描述 | 期望 |
|:---|:---|:---|:---|
| 下边界 - 1 | 3 位 (`abc`) | 刚好不合法 | ✗ 拒绝 |
| **下边界** | **4 位 (`abcd`)** | **最小合法值** | **✓ 接受** |
| 下边界 + 1 | 5 位 (`abcde`) | 明确合法 | ✓ 接受 |
| 上边界 - 1 | 49 位 | 明确合法 | ✓ 接受 |
| **上边界** | **50 位** | **最大合法值** | **✓ 接受** |
| 上边界 + 1 | 51 位 | 刚好不合法 | ✗ 拒绝 |

> **本项目强制要求**：凡是存在 `min/max` 约束的字段（用户名、密码、昵称），接口测试中**必须覆盖下边界 ± 1 和上边界 ± 1 四个点**。

---

#### C. 状态转换测试 (State Transition Testing)

**核心思想**：系统在不同状态之间流转，测试需验证每个合法转换路径，以及所有试图从错误状态触发操作的非法转换。

**应用示例：房间状态机**（参见 [`docs/design/diagrams.md`](../design/diagrams.md)）

```
WAITING ──[双方准备]──► IN_GAME ──[胜负判定]──► ENDED
   ▲                                              │
   └──────────────── 终态，不可逆 ────────────────┘
```

| TC-ID | 测试类型 | 操作 | 期望结果 |
|:---|:---|:---|:---|
| TC-ROOM-P-01 | 合法转换 | WAITING：双方先后准备 | 状态变 IN_GAME，双方收到 WS 通知 |
| TC-ROOM-P-02 | 合法转换 | IN_GAME：落子至胜负判定 | 状态变 ENDED，双方收到结算通知 |
| TC-ROOM-N-01 | 非法转换 | WAITING 状态直接发落子消息 | 返回 `40300 game not active` |
| TC-ROOM-N-02 | 非法转换 | ENDED 状态尝试重新落子 | 接口返回 4xx，状态不变 |

> **规则**：测试矩阵须覆盖**所有有效转换路径**和**与当前阶段相关的主要非法转换**。

---

#### D. 决策表测试 (Decision Table Testing)

**核心思想**：当多个**条件**的不同组合产生不同**输出**时，用决策表穷举关键组合，避免遗漏交叉路径。

**应用示例：落子合法性判断（优先级从高到低短路求值）**

| 条件 \ 规则 | R1 | R2 | R3 | R4 | R5 |
|:---|:---:|:---:|:---:|:---:|:---:|
| 位置已被占用 | ✓ | ✗ | ✗ | ✗ | ✗ |
| 落子后己方气为0（自杀） | - | ✓ | ✗ | ✗ | ✗ |
| 违反劫争规则 | - | - | ✓ | ✗ | ✗ |
| 轮到己方回合 | - | - | - | ✗ | ✓ |
| **期望结果** | `Occupied` | `Suicide` | `Ko` | `NotYourTurn` | 落子成功 |

---

#### E. 正交/成对测试 (Pairwise / Orthogonal Testing)

**核心思想**：当参数组合数量爆炸时，使用成对测试只覆盖每对参数的所有组合，可在大幅减少用例数量的同时保留 75%~90% 的缺陷发现率。

**应用场景**：创建房间时的参数组合

```
棋盘大小: [9×9, 13×13, 19×19]   → 3 种
规则集:   [中规, 日规]            → 2 种
计时模式: [无限制, 每手30s, 包干] → 3 种

全组合 = 3 × 2 × 3 = 18 个用例
成对覆盖 ≈ 9 个用例（覆盖所有两两参数的完整取值组合）
```

> **使用时机**：参数维度 ≥ 3 且全量组合测试成本过高时采用；核心安全路径仍需全量覆盖。

---

#### F. 错误猜测法 (Error Guessing)

**核心思想**：基于经验和直觉，直接针对系统最可能出错的地方编写用例。本项目归纳的高频缺陷模式：

| 模式 | 典型示例 | 测试动作 |
|:---|:---|:---|
| 前后端校验不同步 | 前端允许 3 位密码，后端要求 6 位 | BVA 结合 EP 双层验证 |
| 状态丢失 | 刷新后登录状态消失 | 每个有状态流程插入 `page.reload()` |
| 错误信息被吞 | Toast 只显示"未知错误" | 断言精确 `msg` 文本 |
| 并发竞争 | 两人同时落子最后一口气 | 并发请求模拟 |
| 空指针/nil | 未鉴权时调用用户信息 | 未登录访问所有受保护接口 |
| Token 过期处理 | access_token 过期后请求是否自动续期 | Mock 1h 后场景或直接过期 Token |

### 5.3 覆盖率度量模型 (Coverage Metrics)

不同的覆盖率指标对应不同的质量风险，本项目分层设定目标值：

| 覆盖率类型 | 定义 | 本项目目标 | 适用层 |
|:---|:---|:---|:---|
| **语句覆盖 (Statement)** | 每行代码至少执行一次 | ≥ 80% | 所有层 |
| **分支覆盖 (Branch)** | 每个 `if/else`、`switch` 的所有分支都被执行 | ≥ 90% | biz / engine |
| **条件覆盖 (Condition)** | 复合条件中每个子条件的 true/false 都出现过 | 100% | engine |
| **路径覆盖 (Path)** | 所有可能的代码执行路径 | 核心算法 100% | engine 独立函数 |
| **接口覆盖 (API)** | 每个 Endpoint 至少有一个成功用例和一个失败用例 | 100% | API 层 |
| **E2E 场景覆盖** | P0 功能的 Happy Path + 主要 Error Path | 100% | E2E |

```bash
# 后端按模块查看分支覆盖率
go test -coverprofile=coverage.out -covermode=atomic ./internal/...
go tool cover -func=coverage.out | grep -E "(engine|biz)" | sort -k3 -rn

# 前端覆盖率（vitest）
npm run test -- --coverage
```

**何时覆盖率可以低于目标**：
- 纯胶水代码（如仅做参数透传的 Controller 层）可豁免到 60%。
- 第三方库 wrapper（如 `wsClient.ts` 的底层连接代码）可豁免，但其**业务逻辑分支**不可豁免。

### 5.4 风险优先级矩阵 (Risk-based Prioritization)

用例优先级根据**业务影响 × 缺陷概率**两个维度评估，资源向左上角聚焦：

```
        ┌────────────────────────────────────────┐
高      │  P1: 必测，发版前              P0: 核心路径  │
业      │  (如注册边界值、WS 断线重连)   (如登录、落子) │
务      ├────────────────────────────────────────┤
影      │  P2: 可选                     P1: 重点关注  │
响      │  (如 UI 微像素差异)            (如劫争边缘)  │
低      └────────────────────────────────────────┘
              低缺陷概率                 高缺陷概率
```

| 优先级 | 触发时机 | 典型场景 |
|:---|:---|:---|
| **P0** | 每次 commit，CI 必须通过 | 登录、落子、WS 握手、路由守卫、Token 续期 |
| **P1** | 每次功能分支合并前必须通过 | 注册边界值、房间状态流转、并发落子保护 |
| **P2** | 发版前全量手动或定期定时跑 | 非主流浏览器兼容、UI 视觉回归、极端边界 |

### 5.5 阶段交付门禁检查单 (Phase Gate Checklist)

每个开发阶段交付前，以下用例**必须在 `npm run test:e2e` 中全部为绿色**，否则不允许推进下一阶段。

#### 认证模块 (Auth) — 阶段四已交付
- [x] `TC-AUTH-P-01`：合法注册后返回登录页，Toast 显示"注册成功"
- [x] `TC-AUTH-P-02`：合法登录后跳转 `/lobby`，Cookie 包含 `access_token`
- [x] `TC-AUTH-P-03`：未登录访问 `/lobby` 被重定向至 `/login`（路由守卫）
- [x] `TC-AUTH-P-04`：登录后刷新页面，用户身份和 UI 保持不变（持久化）
- [ ] `TC-AUTH-N-01`：注册已存在用户名，Toast 精确显示 `username already exists`
- [ ] `TC-AUTH-N-02`：用户名 < 4 位，前端**即时拦截**，不发网络请求
- [ ] `TC-AUTH-N-03`：密码 < 6 位，前端**即时拦截**，不发网络请求
- [ ] `TC-AUTH-N-04`：使用错误密码登录，Toast 精确显示 `invalid credentials`
- [ ] `TC-AUTH-P-05`：access_token 过期后，下次请求自动静默刷新，用户无感知

#### 大厅模块 (Lobby) — 阶段五解锁后补充
- [ ] `TC-LOBBY-P-01`：登录后在线用户列表实时出现当前用户
- [ ] `TC-LOBBY-P-02`：另一用户登录，大厅在线列表**实时**更新（WS 推送，非轮询）
- [ ] `TC-LOBBY-P-03`：创建房间后大厅房间列表实时出现新房间
- [ ] `TC-LOBBY-P-04`：刷新页面后大厅数据自动恢复（持久化 + WS 重连）

#### 房间与对局 (Room/Game) — 阶段六解锁后补充
- [ ] `TC-GAME-P-01`：落子后棋盘实时更新，双方视图一致，轮次正确切换
- [ ] `TC-GAME-P-02`：一方断线后重连，棋盘状态完整恢复
- [ ] `TC-GAME-N-01`：落子在已占用位置，拒绝并精确提示 `occupied`
- [ ] `TC-GAME-N-02`：非己方回合落子，拒绝并精确提示 `not your turn`
- [ ] `TC-GAME-N-03`：触发自杀位落子，拒绝并精确提示 `suicide`
- [ ] `TC-GAME-N-04`：触发劫争违规，拒绝并精确提示 `ko`
