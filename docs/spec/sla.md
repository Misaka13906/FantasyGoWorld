# 服务等级协议 (SLA) 与技术规范

> **路径**：[`docs/spec/sla.md`](sla.md)  
> **用途**：定义性能 KPI（延迟/可用性）、数据一致性模型、容错与 Fallback 策略、验收标准。


## 1. 核心性能指标 (KPI)

| 指标 | 目标值 | 测量方法 |
| :--- | :--- | :--- |
| **对局指令延迟 (RTT)** | < 100ms (95th percentile) | 前端发送落子指令到收到服务端 Confirm 包的往返时间。 |
| **观战同步延迟** | < 2.0s | 对局者落子到观战者端棋盘更新的时间差。 |
| **计时器误差** | < 200ms | 客户端显示剩余时间与服务端绝对时间戳的偏差。 |
| **系统可用性 (Uptime)** | 99.9% | 排除计划内维护后的服务在线比例。 |

## 2. 数据一致性模型 (Consistency)

- **对局者 (Players)**: **强一致性 (Strong Consistency)**。必须确保落子顺序编号 (Sequence Number) 连续。任何乱序或确实的数据包必须触发重同步，且在同步完成前禁止后续操作。
- **观战者 (Spectators)**: **最终一致性 (Eventual Consistency)**。允许在网络波动时出现短瞬的进度落后，但系统必须在 3 秒内通过全量快照或增量补丁自动对齐状态。

## 3. 容错与 Fallback 策略 (Reliability)

### 3.1 网络连接异常
- **心跳机制**: 客户端每 1 秒发送一次极简心跳。
- **离线判定**: 服务端连续 3 秒未收到心跳则标记用户为“离线”，并通知对方。
- **断线保护期**: 每个对局者拥有累计 180 秒的“断线保护时长”。保护期内，虽然用户离线，但不扣减其对局基本用时和读秒次数，确保其有足够时间重连。

### 3.2 客户端状态同步
- **状态快照 (Snapshot)**: 每 10 手落子，服务端生成一次棋盘状态快照。
- **快速恢复**: 客户端重连成功后，优先拉取最新快照，再追溯之后的增量手数，确保瞬间恢复棋盘。
- **乐观更新回滚**: 前端预渲染落子，若收到 Server 报错（如劫争违规、落子非空地），必须在 16ms 内完成撤回并提示。

### 3.3 服务器崩溃恢复
- **落子日志 (Action Log)**: 每一步落子指令先行同步写入 Redis（主）及数据库（备）。
- **进程重启恢复**: 服务器实例重启后，根据 RoomID 重新从持久化层加载全量对局指令流，并在 5 秒内重建 WebSocket 回话上下文。

### 3.4 降级与限流 (Degradation & Throttling)
- **API 限流 (Rate Limiting)**: 单个用户 HTTP 接口默认限制 50 次/分钟。
- **WS 消息限流**: 单个 WS 连接上推限制 10 次/秒（保护落子和聊天免受泛洪攻击），超出则静默丢弃或返回错误警告。
- **非核心链路降级**: 当 Redis 或 DB 延迟飙升（>200ms）时，优先切断“大厅百人在线列表广播”等旁路消耗，全力保障并隔离对局室核心长连接链路。

## 4. 验收标准记录 (Acceptance Criteria)

- **[AC-01]**：在丢包率 5% 的网络环境下，对局依然能通过 Sequence 重传保持正确性。
- **[AC-02]**：当服务器进程被手动 Kill 并即刻重启，正在进行的对局能在 10 秒内恢复棋盘及其剩余时间。
- **[AC-03]**：对局双方同时落子（微秒级冲突时），服务端必须通过原子操作保证仅一人成功，另一人收到拒绝并自动回滚本地状态。

## 5. 安全与反作弊
- **后端规则校验**: 所有业务逻辑（围棋规则、计分）均以后端为准。前端代码仅作为 UI 呈现。
- **同 IP 过滤**: 限制同一 IP 在同一房间同时扮演对局双方。
- **Session 绑定**: 每个 WebSocket 连接必须通过 JWT 或 SessionID 与用户账户强关联，防止伪造落子。

## 6. 恢复与容量目标 (Capacity & Recovery)
- **RTO (Recovery Time Objective)**: 服务器或容器宕机后的目标恢复时间 < 30 秒。
- **RPO (Recovery Point Objective)**: 数据丢失容忍度。对局快照及落子（已明确响应给客户端的动作）RPO 为 0（强一致持久化）。
- **单节点并发模型 (Scalability)**: 单体 Go 服务节点需通过调优达到单实例扛住至少 `5,000` 活跃长连接的基准线（即支撑 2,500+ 桌同时对弈）。
